# ADR 0001: процессная модель плеера на pw-cat

Дата: 2026-10-12. Статус: принят (M2).

## Контекст

Плеер v1 — подпроцесс `pw-cat` на клип (`docs/pipewire-recipe.md`).
Требовались решения про время жизни процессов, сигналы и то, как CLI
останавливает воспроизведения, запущенные предыдущим (уже завершившимся)
вызовом CLI.

## Решение

1. **Один потомок `pw-cat` на клип**, запускаемый в собственной группе
   процессов (`Command::process_group(0)`); хэндлы — непрозрачные
   `scheduler::Handle(u64)`, общие для планировщика и плеера.
2. **Остановка = SIGTERM группе процессов, 2 с на милость, затем SIGKILL +
   reap.** `Child::kill` из std умеет только SIGKILL, поэтому сигналы идут
   через минимальную зависимость `libc` (уже в дереве через
   libpulse-sys). Резкие убийства тут безвредны: поток питает null-sink, и
   PipeWire прибирает поток, когда соединение рвётся.
3. **stderr — в файл лога во временном каталоге, никогда не пайп**:
   долгоиграющий потомок не должен блокироваться на переполненном пайпе
   или умирать от SIGPIPE при выходе родителя. Лог удаляется, как только
   потомок доказал свою исправность.
4. **Пробное окно (300 мс) в `play`**: ошибки декодирования выходят за
   миллисекунды, поэтому короткое синхронное окно их всплывает (первая
   строка stderr + код выхода), сохраняя `play` неблокирующим для здоровых
   клипов.
5. **Межпроцессная остановка сканом `/proc/*/cmdline`**: `soundboard play`
   выходит сразу после запуска, поэтому `soundboard stop` находит сирот по
   точной форме аргументов (`--playback --target soundboard [клип]`),
   шлёт им SIGTERM, после паузы — SIGKILL. Зомби считаются ушедшими
   (пустой cmdline). Ручной запуск `pw-cat --target soundboard` тоже
   совпадает — по замыслу.
6. **Без потока-могильщика**: потомки забираются опросом `try_wait` при
   каждом вызове API плеера — простейший корректный вариант и для
   однопоточного CLI, и для главного цикла GTK в M3.

Два места вызова `libc::kill` (`signal_group`/`signal_pid`) — единственные
`unsafe`-блоки в репозитории, и они никогда не создают и не разыменовывают
указатели — `kill` получает только скалярные pid и номера сигналов —
поэтому правило репозитория «нет `unsafe` без записанного ADR» соблюдено,
и этот ADR — та самая запись.

## Рассмотренные альтернативы

- Воспроизведение в процессе через `pulse`/`libpulse`: без зависимости от
  аудио-библиотеки нет декодирования mp3/ogg; отложено до момента, когда
  GUI понадобится метрирование.
- Демон, держащий потомков (state-файл с pid): лишние движущиеся части;
  скан `/proc` не имеет состояния и самолечится от протухших pid.
- Пайпы + фоновый поток-осушитель для stderr: риски SIGPIPE/переполнения
  пайпа без единой выгоды.

## Последствия

- `libc` становится прямой зависимостью (сигналы и больше ничего).
- Осиротевшие `pw-cat` после удаления лога ничего не пишут; убитые
  воспроизведения обрываются на середине клипа (для мемов приемлемо).
- GUI (M3) переиспользует `Player`/`Scheduler` как есть и дополнительно
  получает внутрипроцессные пер-клиповые прерывания через планировщик.
